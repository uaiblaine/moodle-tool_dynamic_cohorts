## 3. Findings

### F01 (minor, verified real): Condition form fragment labels any competency id outside the user's scope

- **Claim:** The `competencyids` autocomplete sets `'valuehtmlcallback' => fn($id) => self::competency_label((int) $id)` (`competency_proficiency.php:85`). `competency_label()` (`:336-351`) reads `{competency} JOIN {competency_framework}` by id, with no scope test and no visibility test. The callback never reads `$this->scope`.
- **Evidence (security reviewer, re-read by the verifier):**
  - Core `lib/form/autocomplete.php` `setValue()` (`:221-222`) adds an option for every submitted or default value of an ajax autocomplete.
  - `export_for_template()` (`:232-235`) and `toHTML()` then call the callback for each option.
  - `lib.php:57-74` builds `condition_form` from client-controlled `jsonformdata` and from `defaults` passed to `set_data()`, and returns `$mform->render()`.
  - The only gate is `rule_access::require_manage($context)` (`lib.php:51-52`).
  - The scope is enforced only later, by `validate_scope()` on submit.
  - `search_competencies.php:82-88` does scope its results with `scoped_contexts_sql('f.contextid', 'f.visible', $scope)`. The fragment is the one path that skips it.
  - No test renders the fragment with an out-of-scope competency id.
- **Failure scenario:**
  1. A user holds `tool/dynamic_cohorts:manage` and `moodle/cohort:assign` in category A only.
  2. They call `core_get_fragment` (component `tool_dynamic_cohorts`, callback `condition_form`, `classname=competency_proficiency`, `contextid=A`, `defaults={"configdata":"{\"competencyids\":[1234]}"}`).
  3. The returned `data-html` carries "Framework › Competency (idnumber)" for competency 1234, even when it sits in category B's hidden framework.
  4. Looping over ids enumerates every competency on the site. The `competencymissing` text also tells existing ids from missing ones.
- **Verifier's reasoning:** The finding is real and the whole path was traced: fragment, `condition_form::get_condition()` (`set_scope`), autocomplete `setValue`, `addOption`, then the callback.

  The verifier downgraded it from major to minor:
  - Only framework shortname, competency shortname and idnumber leak.
  - Only a user who already holds both manage capabilities in some category can trigger it.
  - It still breaks the plugin's scoped-visibility contract for hidden frameworks.
  - The WS submit path is not affected, because it throws on invalid data before it labels anything.
  
  The verifier did not run it, and did not check whether core competency capabilities would expose the same names elsewhere.
- **Suggested fix:** Make the callback scope-aware. When `$this->scope !== null`, return the plain id or `competencymissing` unless the competency's framework passes `scoped_contexts_sql('f.contextid', 'f.visible', $this->scope)`. Add a test that renders the fragment as a category manager with an out-of-scope id and asserts the framework name is absent.

### F02 (minor, confirmed by reading): The modal preview describes a category user's "any course" source as site-wide

- **Claim:** `external/condition_form.php:95` builds the returned description from an instance created in `submit()` (`:87-88`), and its scope is never recorded. `competency_proficiency::get_config_description()` (`:385`) takes the category wording only from `get_recorded_scope()`. That method reads `scopecontextid` from the stored configdata (`condition_base.php:292-296`). `record_scope()` runs later, in `condition_manager::validate_submitted_condition` (around `:287`).
- **Evidence:** Flow reviewer. The consolidator confirmed by reading: `submit()` calls only `set_config_data(retrieve_config_data(...))` before `get_config_description()`, and `record_scope()` is the only writer of `SCOPE_KEY`.
- **Failure scenario:** A category manager adds "proficient in X, any course". The rule form shows "rated in any course". After the save, the rule edit form shows "rated in any course of the category "Y"". The text the manager approved did not describe what the condition does.
- **Suggested fix:** In `submit()`, call `set_scope(condition_scope($context))` and `record_scope()` before `get_config_description()`. Alternatively, let `get_config_description()` fall back to `$this->scope`. `cohort_field.php:455` reads the recorded scope the same way and may share the defect; that was not checked.

### F03 (minor, unverified): `competencysource_help` and PLAN overstate when a course rating reaches the site-wide rating

- **Claim:** The help text says the site-wide rating is the user's proficiency "whichever course or plan it came from". PLAN.md says `add_evidence` "writes usercomp and, in a course or module context, usercompcourse".
- **Evidence:** Core `competency/classes/api.php`:
  - `:4358-4390`, `ACTION_COMPLETE` in a course: writes `usercomp` only when the course's `pushratingstouserplans` is on, and also requires `usercomp` to have no grade unless `overridegrade` is set.
  - `:4394-4425`, `ACTION_OVERRIDE` in a course: skips `usercomp` when push is off.
- **Failure scenario:** An admin picks "Site-wide rating" and expects a user graded in a course to count. If that course does not push ratings to user plans, the user never matches. The class docblock and `get_events()` describe the event correctly. Only the help text and the PLAN mislead.
- **Suggested fix:** Say that a course rating reaches the site-wide one only when the course pushes ratings to user plans. Correct the PLAN sentence the same way.

### F04 (minor, unverified): The learning_plan self-sync guard cannot fire when a new condition is saved

- **Claim:** `get_self_synced_template()` (`learning_plan.php:325-335`) reads the rule through the condition's `ruleid`. `process_condition_json` strips `ruleid` (`condition_manager.php:205-207`), and a new condition has no rule yet. `get_rule()` therefore returns null, the guard returns null, and the save passes. When the guard does run, it decides from the recorded fact (the rule's `cohortid` and `competency_templatecohort`), so it never produces a wrong result.
- **Evidence:** `condition_manager.php:272-309` calls `get_sql()` only when `!is_broken()`. `test_self_synced_template_breaks` (`learning_plan_test.php:201`) covers a stored condition only.
- **Failure scenario:** A rule manager adds a learning_plan condition whose template is cohort-synced to the rule's own cohort. The rule saves with no error. The next cron or event run marks the rule broken, and the author is never told why at save time.
- **Suggested fix:** In `rule_manager::process_form`, where the rule is known, refuse the save or warn when a new condition is broken for a rule-tied reason. Otherwise, accept the late detection and say so in the learning_plan docblock.

### F05 (minor, unverified): `is_broken()` re-runs uncached queries up to three times per rule per event

- **Claim:** On the observer path, `is_broken()` runs three times per condition:
  1. `rule_manager.php:348` calls `rule::is_broken(true)` on instance A.
  2. `condition_manager.php:469-471` builds instance B and calls `is_broken()`.
  3. `B->get_sql()` (`competency_proficiency.php:485`) calls `is_broken()` again.
  
  The per-instance memos (missing ids, self-synced template) save only the repeat on B. `validate_scope()` (two COUNT queries for a scoped global source) and `is_course_missing()` have no memo.
- **Evidence:** `competency_proficiency.php:441`, `:445` and `:455`; `learning_plan.php:442` and `:446`.
- **Failure scenario:** These counts come from reading only. A learning_plan rule costs about 6 statements per event. A scoped one-course competency rule costs about 9-11. A cohort sync that creates plans for 10,000 members fires 10,000 `competency_plan_created` events, which adds about 60,000 statements.
- **Suggested fix:** Pick one:
  - memoise the whole `is_broken()` result per instance, keyed by the config string;
  - pass the instances `process_rule()` already evaluated into `get_matching_users()`;
  - let `get_sql()` trust a `build_sql_data()` that has just checked `is_broken()`.

### F06 (minor, unverified): Competency rating events evaluate every rule on the class, whatever its course or source

- **Claim:** `is_relevant_event()` (`competency_proficiency.php:564-569`) filters on the action and the competency id only. It ignores the configured source and course, although the event's `contextid` names the course.
- **Evidence:** Core `add_evidence()` (`api.php:4330-4440`) writes `usercompcourse` in a course context, and writes `usercomp` only under `pushratingstouserplans`.
- **Failure scenario:** Take a rule "proficient in C, course 7 only". Course completions in 500 other courses rate C for 50,000 users, and each rating processes the rule. The result stays correct, but each of those evaluations is wasted.
- **Suggested fix:** For `SOURCE_COURSE`, compare the course of the evidence context with `courseid`, which the context cache resolves cheaply. Leave the other sources as they are.

### F07 (minor, unverified): The Context filter and column cost one `course_categories` query per context on every system-level rules page view

- **Claim:** The reused core `cohort:context` filter (`rules.php:152-153`) builds its options on each render. It runs `SELECT DISTINCT` over `{context} JOIN {cohort}` and calls `get_context_name()` for each context. For a category, `get_context_name()` runs an uncached `$DB->get_record('course_categories')`. The column callback does the same for each row. The options cover every context that holds a cohort, not only contexts with rules.
- **Evidence:**
  - Core `cohort/classes/reportbuilder/local/entities/cohort.php:255-271`: the options callback.
  - Same file, `:98-107`: the column callback.
  - `lib/classes/context/coursecat.php:81`: the uncached `get_record`.
- **Failure scenario:** Unmeasured. On a site with 300 categories that hold cohorts, a site admin's rules page view costs about 300 extra queries, plus one per row.
- **Suggested fix:** Supply an options callback limited to the contexts of cohorts that have rules, as one query joining `course_categories`. Alternatively, load the options lazily.

### F08 (minor, confirmed by reading): The `MAX_RESULTS` docblock promises a "narrow the search" prompt that does not exist

- **Suggested fix:** Either reword the docblock to "the user narrows by typing", or return a truncation flag and show a hint.

## 4. Refuted findings and corrected claims

- **F04 refuted on re-check by the main session.** `rule_manager::process_form()` calls
  `$rule->is_broken(true)` right after `condition_manager::process_form()` (in the same
  transaction) and calls `mark_broken()`, which also disables the rule. The newly saved condition
  then has its `ruleid`, so `get_self_synced_template()` sees the rule's cohort: the rule is
  broken, disabled and shows the explanatory description at save, not at the next run. This is the
  behaviour owner decision Q4 chose (broken with an explanation, as `cohort_membership` does). What
  remains true: the save itself raises no error.
- **F03 confirmed by the main session** against core `competency/classes/api.php`: in a course or
  module context, `ACTION_COMPLETE` writes `usercomp` only when the course's
  `pushratingstouserplans` is on (`:4366-4378`), and `ACTION_OVERRIDE` skips it when that setting
  is off (`:4432-4435`).

- The moodle reviewer's sub-claim (in F09) that the diff adds "a fifth web service" is wrong. `db/services.php` had 5 ajax functions at `5eb5b73` and has 6 at HEAD, as the comments reviewer said. The finding itself stands.
- The verifier refuted no finding. It rejected only the "major" rating of F01, which it rated minor.

## 5. What each dimension checked and found clean

None of the reviewers ran tests, Behat or `mdl` commands. Everything below was established by reading.

### Moodle standards and APIs

- **search_competencies:**
  - `core_external` imports.
  - Call order: `validate_parameters`, then `context_from_id` (system or category only), then `validate_context`, then `require_manage` (both capabilities), then the category gate and the scoped SQL.
  - Correct PARAM types. The `PARAM_RAW` label is documented, escaped HTML, and pinned by `test_search`.
  - The LIKE search uses `sql_like_escape` and named params once each, with a LIMIT and a deterministic ORDER BY.
  - `db/services.php` has `ajax => true`, read type and the capability. `version.php` was bumped from 2026100504 to 2026100508. There is no schema change, so no upgrade step is needed.
- **Lang strings:**
  - en and pt_br keys are identical, in the same order and sorted.
  - All four `addHelpButton` targets have `_help` strings.
  - Every new key is used. There are no dynamic ids.
- **Condition contract:**
  - The condition hooks are implemented consistently with `cohort_membership` and `user_role`.
  - The four-way SQL truth table is correct. Params use `generate_param_alias`.
  - Core has exactly 3 evidence actions, so the "log leaves the rating" rule is right.
  - Core fills `relateduserid` from a user context.
  - The unlink snapshot carries `origtemplateid`.
- **Autocomplete:**
  - The `valuehtmlcallback` output is escaped once.
  - The force-submission value resolves harmlessly.
  - An empty status choice means "any", not draft.
- **Report builder:** the column and filter use entity components. The filter is system-level only, and tests pin both directions and the orphan row.
- **Observer:**
